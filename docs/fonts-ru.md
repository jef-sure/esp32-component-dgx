# Шрифты для программы: запросы и сборка

[English version](fonts-en.md)

Как программа на DGX получает шрифты нужного размера с нужными буквами,
не запуская ничего руками: компоненты и сама программа запрашивают шрифты в
своих CMakeLists, а DGX делает их все один раз при сборке. Записка для
того, кто впервые это видит; устройство механизма — в конце.

## Задача

DGX рисует текст матричными шрифтами: буква — картинка из точек, сделанная
заранее под один размер в пикселях. Шрифт делает конвертер `font2c` из
файла TTF или OTF, какой есть на компьютере, и кладёт его в пару файлов
`.c` и `.h`. Несколько шрифтов встроено в DGX (`src/fonts/`), но для
программы их обычно мало: нужен другой размер, другие буквы, кириллица,
умляуты.

Шрифты нужны не только программе. Экранная клавиатура из DGX-DI рисует
подписи клавиш, и у раскладки свои буквы и свой размер в миллиметрах.
Игровой движок DGX-GE показывает диалоги шрифтом, который на дисплее
другого размера должен быть другого размера в пикселях. Если каждый будет
делать шрифты сам, выйдет два шрифта одного начертания с разными наборами
букв, одинаковые имена функций в двух файлах и зависимость от того, кто
соберётся первым.

Поэтому шрифты — дело DGX, в одном месте:

- каждый, кому нужен шрифт, пишет в своём CMakeLists **запрос**: имя, буквы
  и откуда шрифт;
- в конце конфигурации DGX собирает все запросы в одно правило сборки;
- при сборке один скрипт делает все шрифты сразу: на одно начертание в
  одном размере — один шрифт с буквами всех, кому он нужен;
- программа получает заголовок `dgx_fonts.h` с функцией на каждый запрос.

Ничего снаружи до CMake запускать не нужно. Проект без запросов ничего не
генерирует и ничего от компьютера не требует.

## Как это выглядит

В `main/CMakeLists.txt` программы, после `idf_component_register`:

```cmake
# плата: дисплей 1280x800 на 217x136 мм; кадр игры показан вчетверо крупнее
dgx_fonts_board(PIXELS 1280 800 MM 217 136)
dgx_fonts_scale(4)
# правила подбора начертаний, когда запрос не называет точное (файл описан ниже)
dgx_fonts_rules(../fonts.rules)

# текст игры: 12 точек кадра, моноширинный, с буквами всех строк игры
dgx_font_need(text SIZE 12pt MONO TEXTS assets/ru.po assets/pop.pot)
# рукописный шрифт DGX как есть; у него нет скобок подстановок {0}, они не нужны
dgx_font_need(hand DGX font0ss TEXTS assets/ru.po EXCEPT "{}")
# шрифт программы как есть, в нём нужны только цифры и двоеточие
dgx_font_need(time FILE fonts/PxCgaThin8.c LETTERS "0123456789:")
# шрифт подписей клавиатуры: dgx-di сам читает свою раскладку и делает запрос за программу
dgx_di_keyboard_font(keys keys.json)
```

Компонент пишет то же в своём CMakeLists, например заголовки своих
виджетов высотой 4,5 мм:

```cmake
idf_component_register(SRCS "widgets.c" INCLUDE_DIRS "." REQUIRES dgx)
dgx_font_need(title SIZE 4.5mm TEXTS title.txt)
```

В коде — заголовок и функция по имени запроса:

```c
#include "dgx_fonts.h"

dgx_font_string_utf8_screen(scr, 10, 40, "Привет", ink, DgxOutputNormal, 1, dgx_font_text(), NULL, NULL);
dgx_di_keyboard_open(&kb, scr, DGX_FONTS_BOARD_WIDTH_MM, DGX_FONTS_BOARD_HEIGHT_MM, keys, keys_size, dgx_font_keys(), &field);
```

При `idf.py build` в логе появляется строка на каждый запрос:

```
title: DejaVu Sans Mono Book 27 px (4.5 mm), 24 glyphs
text: DejaVu Sans Mono Book 48 px (12 pt x 4), 97 glyphs
hand: font0ss of DGX, used as is
time: PxCgaThin8.c of the program, used as is
keys: DejaVu Sans Book 24 px (4 mm), 148 glyphs
```

## Запрос

Запрос — одна строка `dgx_font_need(<имя> ...)` (need — «нужен» по-английски).
Имя — идентификатор C: по нему называется функция `dgx_font_<имя>()`. Имя,
совпадающее с функцией самого DGX (`dgx_font_string_bounds` и подобные),
отвергается, как и два имени, различающиеся только регистром: их макросы
не различались бы. Одно имя в двух местах, в компоненте и в программе, с
одними и теми же словами — это один запрос: буквы обоих складываются до
выбора начертания. С разными словами обоим должен достаться один и тот же
шрифт; разные шрифты под одним именем — ошибка сборки, с обоими местами и
обоими шрифтами. Слово, повторённое в одном запросе, — ошибка, а не
молчаливое второе значение.

Слова запроса:

| Слово | Что значит |
| --- | --- |
| `TEXTS <файлы...>` | Файлы, все буквы которых шрифт должен иметь. Пути от CMakeLists, где написан запрос. Как читается файл — ниже. |
| `LETTERS "<буквы>"` | Буквы как есть, в дополнение к текстам или вместо них; любые знаки, скобки, точки с запятой и пробелы тоже. |
| `EXCEPT "<буквы>"` | Буквы текстов, которые шрифту иметь не нужно: скобки подстановок `{0}` в строках игры, например. |
| `SIZE <n>pt`, `<n>mm`, `<n>px` | Размер шрифта: в точках кадра, в миллиметрах или в пикселях (ниже). Без единицы — точки. |
| `MONO` | Только моноширинное начертание. |
| `FAMILY "<образец>"` | Только это семейство; образец с `*`, как в правилах. |
| `POSTSCRIPT <имя>` | Точное начертание по его PostScript-имени (`DejaVuSans`, `DejaVuSans-Bold`): правила не нужны. |
| `SOURCE <файл>` | Шрифт из этого файла: любой файл шрифта, который читает `font2c`, — TTF, OTF или BDF — с `SIZE` (шрифт из картинок — только в том размере, какой в нём есть), либо JSON рукописного шрифта из редактора hw-fonts без размера. |
| `DGX <имя>` | Встроенный шрифт DGX как есть: `font0ss`, `TerminusTTFMedium12` и другие из `src/fonts/`. |
| `FILE <файл.c>` | Готовый шрифт программы как есть; программа компилирует его сама, DGX только проверяет буквы и даёт функцию. |
| `PATCH <файл>` | Глифы этого шрифта, исправленные руками в редакторе шрифтов (см. [Глифы, исправленные руками](#глифы-исправленные-руками)); без него патч ищется по имени шрифта. |

Откуда шрифт, говорит ровно одно из: `SIZE` с `MONO`/`FAMILY` (подбор по
правилам), `SIZE` с `POSTSCRIPT`, `SOURCE`, `DGX`, `FILE`. У шрифта «как
есть» (`DGX`, `FILE`) размер свой, `SIZE` ему не пишут. `POSTSCRIPT` и
`SOURCE` сами называют начертание, `MONO` и `FAMILY` к ним не пишут: запрос с
тем и другим — ошибка.

Шрифты делятся на два рода:

- **сделанные** — DGX сделал их конвертером под эту плату из TTF, OTF или
  JSON: `SIZE`, `SOURCE`;
- **как есть** — уже готовые `.c`: `DGX`, `FILE`.

## Запросы в файле

Обычно запросы пишут прямо в CMakeLists, и этого достаточно. Файл нужен в
одном случае: когда у программы две сборки. Игровой движок, например,
собирается не только под плату через ESP-IDF, но и на компьютере обычным
Makefile, для своих проверок; там CMake не запускается, запросы из
CMakeLists ему не видны, а шрифты нужны те же самые. Тогда запросы кладут в
файл, который читают обе сборки.

В файле те же слова, что у `dgx_font_need`, только по одному на строку и
строчными буквами; запрос начинается строкой `need <имя>`:

| В CMakeLists | В файле |
| --- | --- |
| `dgx_font_need(text SIZE 12pt MONO TEXTS a.po b.po)` | `need text` / `size 12pt` / `mono 1` / `text a.po` / `text b.po` |
| `FAMILY "DejaVu*"`, `POSTSCRIPT DejaVuSans` | `family DejaVu*`, `postscript DejaVuSans` |
| `DGX font0ss`, `FILE f.c`, `SOURCE f.ttf` | `dgx font0ss`, `file f.c`, `source f.ttf` |
| `LETTERS "0123456789:"`, `EXCEPT "{}"` | `letters 0123456789:`, `except {}` |

Пример, `main/fonts.needs` игры:

```
# шрифты игры: одни и те же для платы и для хоста
need text
size 12pt
mono 1
text assets/pop.letters
need hand
dgx font0ss
text assets/pop.letters
```

Сборка под плату: в CMakeLists вместо ряда `dgx_font_need` одна строка,
остальное (плата, масштаб, правила) как обычно:

```cmake
dgx_font_needs_file(fonts.needs)
```

Сборка на компьютере: тот же файл, тот же скрипт, без CMake. Масштаб,
дисплей и правила, которые под плату говорит CMakeLists, здесь идут
аргументами. Получаются те же `dgx_fonts.c` и `dgx_fonts.h` в названном
каталоге; их компилируют в программу хоста с `-I` на этот каталог:

```sh
python3 components/dgx/font2c/dgx_fonts.py build main/fonts.needs build-host/dgx_fonts \
        --scale 4 --pixels 1280 800 --mm 217 136 --rules fonts.rules
cc ... -Ibuild-host/dgx_fonts build-host/dgx_fonts/dgx_fonts.c ...
```

Пути в файле считаются от его каталога. Если программа собирается для одной
платы, строки `rules <файл>`, `scale <n>`, `board pixels <w> <h>` и
`board mm <w> <h>` можно написать прямо в файле; аргументы командной строки
важнее строк файла. Правка файла переконфигурирует проект сама, как правка
CMakeLists.

## Размер и плата

Размер из запроса переводится в пиксели дисплея один раз, при сборке:

| Единица | Пикселей | Нужно от платы |
| --- | --- | --- |
| `12pt` | 12 × масштаб кадра: игра показывает свой кадр крупнее | `dgx_fonts_scale`, без него 1 |
| `4.5mm` | 4,5 × (пикселей на миллиметр дисплея) | `PIXELS` и `MM` |
| `30px` | 30 | ничего |

Масштаб — одно число: во сколько раз плата показывает кадр программы
крупнее. Игра рисует кадр 320x200 в точках, 10-дюймовый дисплей показывает
его в 1280x800, точка — четыре пикселя, масштаб 4; на 7-дюймовом та же игра
берёт 3; программа без кадра масштаб не задаёт, и точка равна пикселю.
Масштаб ничего не рисует и не увеличивает: он только переводит точки в
пиксели, когда делаются шрифты, и возвращается программе числом
`DGX_FONTS_SCALE`. Запрос `text SIZE 12pt` при масштабе 4 даёт шрифт,
сделанный из TTF сразу в 48 px: настоящие 48-пиксельные буквы, а не
12-пиксельные, увеличенные квадратами, и программа рисует им со `scale` 1
(`DGX_FONT_TEXT_MADE` 1). Шрифт «как есть», `time FILE PxCgaThin8.c`,
остаётся в точках кадра (`DGX_FONT_TIME_MADE` 0), и программа рисует им
текстовым API с целым `scale`, равным масштабу: 8 × 4 = 32 пикселя,
квадратные нарочно, как у пиксельного шрифта и положено.

Дисплей и масштаб программа задаёт отдельно: `dgx_fonts_board(PIXELS 1280
800 MM 217 136)` — факт платы, `dgx_fonts_scale(4)` — выбор игры на этой
плате. Пикселей на миллиметр считается по ширине; если по высоте выходит
заметно иначе (больше 5%), сборка останавливается: числа дисплея
перепутаны. Результат округляется до целого пикселя, половины вверх: 4 мм
на дисплее с 5,9 px/мм — 24 px.

Запрос в миллиметрах без `PIXELS`/`MM` — ошибка сборки с подсказкой, чего
не хватает. Дисплей и масштаб, сказанные дважды с теми же числами, не
ошибка, с другими — ошибка с обоими значениями: файл платы может давать
числа, а вызов делать программа один раз.

## Буквы

В шрифт попадают только те буквы, которые просят: буквы текстов запроса и
`LETTERS`, без `EXCEPT`. ASCII сам по себе не добавляется: шрифту часов
из `LETTERS "0123456789:"` незачем 85 лишних глифов. Файлы `TEXTS`
читаются по смыслу, а не как набор байтов:

| Файл | Что берётся |
| --- | --- |
| `.po`, `.pot` | Строки `msgid`, `msgid_plural` и `msgstr`, с переносами строк и экранированием как в gettext; заголовок файла (запись с пустым `msgid`) пропускается. |
| `.json` | Все строковые значения. |
| любой другой файл | Весь файл: текст в UTF-8. |

Строки, которые программа собирает на ходу — номер уровня, минуты, время, —
в текстах не стоят, там только подстановки вроде `{level}`: их знаки просят
через `LETTERS "0123456789:-"` или через файл букв, который пишет сама
программа, упаковщик игры, например.

Текстовый файл с меткой порядка байтов (BOM) читается без неё.
Управляющие и форматирующие знаки (перевод строки, табуляция, мягкий
перенос, соединитель нулевой ширины) буквами не считаются; всё остальное
считается, в том числе значки шрифта иконок из области для частного
использования.
Пробел берётся в сделанный шрифт, если он есть в текстах, но от шрифта
«как есть» никогда не требуется: пробел умеет каждый шрифт DGX, у
рукописного он задан шириной, а не глифом.

Если шрифту не хватает букв, сборка останавливается и называет их:

```
dgx_fonts.py: needs.txt:15: font0ss of DGX: lacks the characters { U+007B } U+007D
```

Так и возникло `EXCEPT "{}"` в примере выше: в строках игры есть
подстановки `{0}`, а рукописному шрифту они ни к чему. Запасного шрифта на
случай нехватки букв нет: тихая дырка в тексте хуже остановки.

## Правила подбора

Когда запрос не называет точное начертание, его выбирают **правила** —
текстовый файл программы, `dgx_fonts_rules(fonts.rules)`. Какой TTF
переводится в монохром без искажений в каком размере, решает человек, а
не программа; правила — его слово. Без правил запрос по семейству или
`MONO` — ошибка.

```
# откуда брать шрифты
source system                  # установленные на компьютере (fontconfig)
# source dir  ~/Fonts          # все .ttf, .otf, .ttc в каталоге, вглубь
# source list ~/fonts.txt      # файл со списком файлов шрифтов, по одному на строку

# что допустимо и в каких размерах, в порядке предпочтения
allow "Terminus (TTF)*"   12, 14, 16, 18, 20, 22, 24, 28, 32
allow "DejaVu Sans Mono"  16..
allow "IBM Plex Mono"     28..
deny  "Comic*"
allow *                   40..
```

- `allow "<семейство>" <размеры>`: семейство — образец с `*` (имя
  семейства или «семейство начертание», регистр не важен). Размеры — в
  пикселях дисплея: числа через запятую, промежутки `16..24`, `16..`,
  `..24`, сравнения `> 12`, `>= 12`, `< 40`, `<= 40`; `&` — «и», запятая
  или пробел между условиями — «или».
- `deny "<семейство>" [<размеры>]` — нельзя; без размеров — ни в каком.
  Запрет действует на все шрифты программы, а не только на подобранные
  правилами: см. [Шрифты и лицензии](#шрифты-и-лицензии).
- `strict` отдельной строкой пускает только шрифты, названные в строках
  `allow`, как бы их ни запросили. Без этого слова строгого режима нет.
- Берётся первое `allow` по порядку, под которое есть начертание нужного
  размера **со всеми буквами запроса**; среди его начертаний сначала
  обычное, потом Medium, потом жирные, наклонные и остальные, а дальше
  решает порядок источников. Начертание без нужных букв пропускается, как
  и запрещённое.
- Относительный путь в строке `source dir` или `source list` считается от
  файла правил, а относительный путь в списке источников — от этого списка.
- Нет ни одного — сборка останавливается и говорит, какой размер и какие
  буквы искала.

Шрифты берутся с компьютера, где собирают: на другой машине выбор может
быть другим, а без подходящего сборка остановится. Точное начертание по
PostScript-имени ищется через `fc-list` и совпадает буква в букву;
`fc-match` не используется, потому что на незнакомое имя он молча даёт
другой шрифт.

## Шрифты и лицензии

DGX берёт те шрифты, которые просят программа и её компоненты, и их
лицензий не проверяет. Можно ли поставлять шрифт в своём изделии, решает
автор программы, а сборка выкладывает всё нужное для этого на виду.

**Что попало в программу.** Каждый раз, когда делаются шрифты, сборка
пишет `build/dgx_fonts/fonts-used.txt`: каждый шрифт программы, файл, из
которого он сделан, что этот файл говорит о своих правах и лицензии
(таблица `name` у TTF и OTF), и какие запросы и списки его используют.
Путь к нему печатается при конфигурации и ещё раз при сборке, и на него
же ссылается `dgx_fonts.h`. Прочитайте его перед выпуском и ещё раз после
того, как добавили компонент, который просит шрифты.

```
DejaVu Sans Book
  file: /usr/share/fonts/truetype/dejavu/DejaVuSans.ttf, PostScript name DejaVuSans
  version: Version 2.37
  copyright: Copyright (c) 2003 by Bitstream, Inc. All Rights Reserved. ...
  license: Fonts are (c) Bitstream (see below). DejaVu changes are in public domain. ... (shortened; the whole text is in the font file)
  license URL: http://dejavu.sourceforge.net/wiki/index.php/License
  used by: keys at 24 px, named by its PostScript name in /work/components/kbd/CMakeLists.txt

TerminusTTFMedium12, a font of DGX
  file: .../src/fonts/TerminusTTFMedium12.c
  made from: Terminus (TTF) Medium 4.47 at 12 px
  license: SIL Open Font License 1.1
  used by: clock, used as is, in /work/main/CMakeLists.txt
```

Если файл шрифта ничего не говорит о лицензии, так и написано: «the file
says nothing of its copyright or license». Шрифт, который программа
приносит готовым на C (`FILE`), идёт без лицензии: откуда он, знает только
программа.

**Как не пустить шрифт.** Запретить его в правилах программы:

```
deny "Arial*"
```

Запрещённое начертание правила никогда не выберут. Если запрос или список
называет запрещённый шрифт точно — через `POSTSCRIPT`, `SOURCE`, `DGX`,
`FILE` или строкой `dgx_font_list`, — сборка останавливается, и сообщение
называет обе стороны:

```
dgx_fonts.py: /work/components/kbd/CMakeLists.txt: keys asks for DejaVu Sans Book
(/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf) at 24 px, and /work/fonts.rules:7 denies it:
the request and the rules disagree, one of them must change
```

Другое начертание DGX вместо запрещённого не подставляет: компонент,
попросивший шрифт по имени, либо получает его, либо сборка
останавливается. Правила есть только у программы, поэтому решает
программа, и компонент их не обойдёт.

- Запрет с размерами, `deny "DejaVu Sans" < 20`, не пускает начертание
  только в этих размерах. У шрифта «как есть» (`DGX`, `FILE`) размера для
  сравнения нет, поэтому его касается только запрет без размеров.
- Шрифт «как есть» сравнивается по имени без пробелов и знаков
  препинания, как их отбрасывает font2c: `deny "DejaVu Sans*"` ловит и
  `DejaVuSansBook32`, а `deny "Terminus (TTF)*"` — `TerminusTTFMedium12`. Шрифт DGX сравнивается
  ещё и по семейству из `src/fonts/README.md`.
- Если каждый запрос называет начертание точно, хватит правил из одних
  строк `deny`, без `source`. Запросу, которому начертание подбирают
  правила, источник по-прежнему нужен.

**Строгие правила.** Если вы проверили лицензии некоторого набора шрифтов
и хотите, чтобы на всём остальном сборка останавливалась, добавьте в
правила слово `strict`. Тогда шрифт пускается, только если его называет
строка `allow`, — подбирают ли его правила или запрос называет его точно:

```
strict
source dir ~/fonts-checked
allow "Terminus (TTF)*"  12..32
allow "DejaVu Sans*"     8..
allow "Weather Icons"    1..
```

Размеры в строках `allow` по-прежнему выбирают начертания для запросов,
которым их подбирают правила; шрифту, названному точно, достаточно строки
`allow` с его семейством, размер не важен. `allow *` пускает всё и
отменяет смысл `strict`. Без слова `strict` правила работают как описано
выше.

**Шрифты DGX.** Шрифты в `src/fonts/` сделаны из шрифтов со свободными
лицензиями или нарисованы для DGX. Из чего сделан каждый и под какой
лицензией, записано в `src/fonts/README.md`.

## Один шрифт на начертание и размер

Запросы уходят в `font2c` одним списком, по строке на запрос, и он сам
сводит их к парам (начертание, размер в пикселях): на пару делается один
шрифт с объединёнными буквами всех её запросов, а каждый запрос получает
свою функцию, указывающую на него. Если игра просит «DejaVu
Sans Mono 48 px с буквами диалогов», а клавиатура — «то же начертание в
8,1 мм», которые на этой плате тоже 48 px, во флеш идёт один набор глифов, и
`dgx_font_text()` с `dgx_font_keys()` возвращают один и тот же шрифт.

Рукописный шрифт из JSON размера не имеет (его задают при рисовании), на
один файл — один шрифт.

## Глифы, исправленные руками

В мелких размерах глиф после конвертера иногда выходит на панели кривым:
разорванная ножка, буква не на своей строке, ударение не на месте. Редактор
шрифтов DGX, `font-editor/index.html`, открывает `.c`, записанный `font2c`,
даёт перерисовать глифы по точкам, поменять их размер, шаг и смещения или
подогнать их к точкам и сохраняет исправления как **патч**. Сам `.c` руками
не правят: `font2c` делает его заново из начертания и патча, и каждый глиф
патча целиком заменяет нарисованный FreeType, со своим размером и
метриками. Шрифт, сделанный заново, исправления сохраняет.

Редактор сохраняет один патч на весь `.c`: в нём по части на каждый шрифт
файла, где что-то изменено. Часть называет свой шрифт — тем именем, которое
ему даёт `font2c` (семейство, стиль и размер без пробелов и знаков, как
`DroidSansRegular9`), — и его размер; `font2c` даёт каждому шрифту ту часть,
что называет его. Патч `.c` с одним шрифтом называется по шрифту,
`DroidSansRegular9.patch.json`; патч `.c` с несколькими, как
`build/dgx_fonts/dgx_fonts.c`, — по файлу, `dgx_fonts.patch.json`. Патч,
названный для шрифта (в `PATCH` или именем файла), где части для него нет,
`font2c` отвергает.

Шрифт, который делается при сборке, берёт свой патч сам:

1. файл, названный в `PATCH` (или `patch` в файле запросов), если он есть;
2. иначе `.patch.json` с частью для этого шрифта рядом с CMakeLists или
   файлом запросов, где объявлен запрос;
3. затем рядом с файлом `SOURCE`, если он у запроса есть;
4. затем в `src/fonts/` DGX, где DGX хранит исправления начертаний, из
   которых сделаны его собственные шрифты.

Берётся первый найденный. Два патча в одном каталоге с частью для одного и
того же шрифта останавливают сборку, оба названы. Патч, добавленный или
изменённый в одном из этих мест, при следующей сборке пересобирает шрифты. Шрифт «как есть» (`DGX`,
`FILE`) не патчится: это уже `.c`, сделанный со своим патчем, если тот был.
В патче могут быть глифы, которых шрифту не нужно; они пропускаются, так что
один патч служит всем запросам этого начертания и размера, какие бы буквы
каждый ни просил.

`font2c` берёт те же патчи и напрямую: `-p <файл>` называет патч, `-P
<каталог>` (можно несколько) ищет в каталоге патч с частью для шрифта. Оба
ключа можно писать и в строке списка `-jo`.

## Что получается

В каталоге сборки, `build/dgx_fonts/`, появляются `dgx_fonts.c` и
`dgx_fonts.h`; первый компилируется в библиотеку DGX, второй доступен
всем, кто зависит от DGX. Рядом лежит `fonts-used.txt` со списком шрифтов
и их лицензий (см. [Шрифты и лицензии](#шрифты-и-лицензии)). В заголовке на каждый запрос:

```c
/* text: DejaVu Sans Mono Book at 48 px (12 pt x 4), made for this board */
dgx_font_t *dgx_font_text(void);
#define DGX_FONT_TEXT_MADE 1
#define DGX_FONT_TEXT_PX 48

/* keys: DejaVu Sans Book at 24 px (4 mm), made for this board */
dgx_font_t *dgx_font_keys(void);
#define DGX_FONT_KEYS_MADE 1
#define DGX_FONT_KEYS_PX 24
#define DGX_FONT_KEYS_MM 4

/* hand: font0ss of DGX, used as is: its own function */
#define dgx_font_hand font0ss
#define DGX_FONT_HAND_MADE 0

/* every need, in declaration order: X(name) for each */
#define DGX_FONT_NEEDS(X) X(title) X(text) X(hand) X(time) X(keys)

/* the frame scale and the display the fonts were made for, as declared in the project's CMakeLists */
#define DGX_FONTS_SCALE 4
#define DGX_FONTS_BOARD_WIDTH_PX 1280
#define DGX_FONTS_BOARD_HEIGHT_PX 800
#define DGX_FONTS_BOARD_WIDTH_MM 217
#define DGX_FONTS_BOARD_HEIGHT_MM 136
```

- `dgx_font_<запрос>()` — шрифт запроса, обычный `dgx_font_t *`. У шрифта
  «как есть» это не функция-переходник, а макрос на его собственную
  функцию: `dgx_font_hand()` и есть `font0ss()`. Поэтому библиотека DGX
  не ссылается на код программы, и порядок библиотек при линковке не
  важен; шрифт программы (`FILE`) заголовок объявляет сам.
- `DGX_FONT_<ЗАПРОС>_MADE` — 1, если шрифт сделан под эту плату (его
  размер уже в пикселях дисплея, текст рисуется с `scale` 1); 0, если это
  рукописный шрифт, размер которого выбирается при выводе текста, или шрифт,
  взятый как есть (программа масштабирует его сама, как движок DGX-GE рисует
  пиксельный шрифт полосы ×4, а перо — по высоте строки).
- `DGX_FONT_<ЗАПРОС>_PX`, `_MM` — размер сделанного шрифта в пикселях и, для
  запроса в миллиметрах, запрошенные миллиметры: клавиатура может проверить,
  что ей дали шрифт под её раскладку.
- `DGX_FONT_NEEDS(X)` — все запросы по порядку объявления, для собственных
  дел программы: перечислить свои шрифты, напечатать их имена:

```c
#define NAME(n) #n,
static const char *const names[] = {DGX_FONT_NEEDS(NAME)};
```

  Порядок идёт по всем компонентам, так что таблицу по номерам, как у
  игры или библиотеки, по нему не строят. Такая таблица собирается по
  именам, и пропущенный запрос тогда ошибка компиляции, а не чужой шрифт:

```c
static dgx_font_t *(*const fonts[POP_FONT_COUNT])(void) = {
    [POP_FONT_TEXT] = dgx_font_text, [POP_FONT_HAND] = dgx_font_hand, [POP_FONT_TIME] = dgx_font_time,
};
```

- `DGX_FONTS_SCALE` и `DGX_FONTS_BOARD_*` — числа из `dgx_fonts_scale` и
  `dgx_fonts_board`, чтобы масштаб и дисплей в миллиметрах были записаны в
  проекте один раз: те же числа идут в `dgx_di_touch_display()` и
  `dgx_di_keyboard_open()`.

## Что нужно на компьютере

ESP-IDF уже приносит Python. Проекту с запросами нужны ещё:

| Что | Зачем | Если нет |
| --- | --- | --- |
| CMake 3.19 или новее | собрать запросы в конце конфигурации (`cmake_language(DEFER)`); CMake из инструментов ESP-IDF новее | «the fonts made at build time need CMake 3.19 or later» на первом запросе; проект без запросов не затронут |
| компилятор C для компьютера и заголовки FreeType (`libfreetype-dev`, `pkg-config`) | собрать `font2c` из исходника DGX; он собирается в `build/dgx_fonts/` и пересобирается, когда меняется его исходник | «the FreeType development files (libfreetype-dev) are not installed» |
| fontconfig (`fc-list`, `fc-scan`) | найти начертания: установленные и в каталогах из правил | «fontconfig is required to find fonts» |
| шрифты, которые разрешают правила или называет запрос | сделать из них глифы | «no face allowed by the rules at 48 px has all the characters», «no installed face has the PostScript name …» |

Проект без единого запроса ничего из этого не требует.

## Запросы из другого компонента

Компонент делает запросы так же, как программа: `dgx_font_need` в своём
CMakeLists после `idf_component_register`, как заголовки виджетов в примере
выше. Пути в запросе — от его CMakeLists, функцию `dgx_font_<имя>()` он
зовёт в своём коде, а программе ничего делать не надо: её сборка соберёт и
эти шрифты. Что при этом учесть:

- Компонент зависит от DGX (`REQUIRES dgx`, с реестром `jef-sure__dgx`):
  заголовок `dgx_fonts.h` лежит на путях включения библиотеки DGX.
- Имена запросов общие на весь проект. Запрос компонента с тем же именем,
  что у программы, сольётся с ним, если шрифт тот же, и остановит сборку,
  если нет. Своим запросам компонент даёт имена со своим префиксом
  (`widgets_title`); имя, которое выбирает программа, как `keys` у
  клавиатуры, он берёт аргументом.
- Плату, масштаб и правила объявляет программа, не компонент: плата её.
  Запрос в миллиметрах без платы остановит сборку с подсказкой, что
  объявить.
- Рабочая копия DGX вместо компонента из реестра: на неё должен указывать
  `override_path` в `idf_component.yml` программы. Называться
  `jef-sure__dgx` каталог должен, только когда DGX требует другой компонент
  из реестра: ESP-IDF называет локальный компонент по каталогу, а такой
  компонент ждёт именно это имя. Без `override_path`
  копия в `components/` проигрывает: менеджер компонентов всё равно скачает
  `jef-sure/dgx` из реестра, `project_include.cmake` локальной копии не
  выполнится, и `dgx_fonts_board` окажется неизвестной командой.

Компонент со своим форматом файлов, из которого следует запрос, знает этот
формат сам; DGX знает только свои слова. Такой компонент даёт в своём
`project_include.cmake` функцию-обёртку, которую программа зовёт вместо
`dgx_font_need`: на конфигурации обёртка читает свой файл средствами CMake
(`string(JSON)`), выписывает нужные буквы в файл в каталоге сборки, только
когда они изменились, и делает обычный `dgx_font_need` с обычными словами.
Свой файл обёртка ставит в зависимости конфигурации
(`CMAKE_CONFIGURE_DEPENDS`), чтобы его правка переконфигурировала проект, а
без `dgx_font_need` (DGX старше 0.7.2) останавливается с понятным
сообщением. Так DGX-DI делает шрифт подписей своей клавиатуры:

```cmake
dgx_di_keyboard_font(keys main/keys.json)
```

Обёртка берёт из раскладки поле `font` (`postscript` и `mm`, либо `dgx`) и
подписи клавиш (`label`, а без него `char` и `upper`), пишет их в
`build/dgx_di/keys.letters` и зовёт `dgx_font_need(keys SIZE 4.5mm
POSTSCRIPT DejaVuSans TEXTS build/dgx_di/keys.letters)`. Клавиатуре
программа даёт `dgx_font_keys()`, размер дисплея в мм — тот же, что в
`dgx_fonts_board`: `DGX_FONTS_BOARD_WIDTH_MM`, `_HEIGHT_MM`.

Компонент, который собирается ещё и на компьютере, как игровой движок,
держит запросы в файле формата DGX («Запросы в файле»): его обёртка отдаёт
файл в `dgx_font_needs_file`, а хост-сборка запускает на том же файле
`dgx_fonts.py build`.

## Списки для font2c

Список — второй путь рядом с запросами, для компонента или программы,
которые сами знают свои файлы шрифтов и буквы: текстовый файл, где каждая
строка — аргументы одного обычного запуска `font2c` для любого файла
шрифта, который он читает, BDF тоже (шрифт из картинок — в том размере,
какой в нём есть), пути от списка, `#` —
комментарий:

```
# fonts.list: шрифты виджетов
-n widgets_title DejaVuSans.ttf 24 0x20 0x7e 0xc4 0xdc
-n widgets_note -f note.letters DejaVuSans.ttf 18
DejaVuSans.ttf 30 0x30 0x39
```

В CMakeLists компонента — `dgx_font_list(fonts.list)`: шрифты списка идут в
тот же `dgx_fonts.c`, их функции объявлены в том же `dgx_fonts.h`. Строка
без `-n` получает имя из семейства и размера с приставкой из имени
выходного файла: `dgx_fonts_DejaVuSansBook30`. Одно начертание в одном
размере делается один раз, кто бы его ни просил, список или запрос.

Без CMake и без запросов `font2c` обрабатывает такой список сам:

```sh
font2c -jo fonts.list -jo more.list -o my_fonts     # my_fonts.c и my_fonts.h
```

## Инструмент руками

Тот же скрипт, `font2c/dgx_fonts.py`, отвечает на вопросы без сборки:

```sh
python3 font2c/dgx_fonts.py pick fonts.rules 48 --mono --letters "Привет"   # какое начертание возьмут
python3 font2c/dgx_fonts.py list fonts.rules 48                            # все допустимые, по порядку
python3 font2c/dgx_fonts.py letters assets/ru.po main/keys.json            # какие буквы дают тексты
python3 font2c/dgx_fonts.py json build/dgx_fonts/dgx_fonts.c --font dgx_font_keys  # шрифт как JSON с точками глифов, для редакторов
```

У `font2c` появились ключи `-jo <список>` (можно несколько) и `-o <имя>`:
все шрифты списков в одном `имя.c` с `имя.h`, одинаковые слиты, массивы
названы по шрифту, так что столкновений нет; и `-n <имя>` для одиночного
запуска: функция и файлы по этому имени, массивы с ним в приставке; `-p
<файл>` и `-P <каталог>` накладывают патч редактора шрифтов (см.
[Глифы, исправленные руками](#глифы-исправленные-руками)). Без ключей вывод
прежний.

## Как это устроено

Для любопытных и для того, кто будет это чинить.

1. **`project_include.cmake` компонента DGX.** ESP-IDF включает такой файл
   каждого компонента раньше, чем CMakeLists любого из них. В нём
   определены `dgx_font_need`, `dgx_font_needs_file`, `dgx_fonts_scale`,
   `dgx_fonts_board` и `dgx_fonts_rules`; они ничего не запускают, а только складывают свои слова в глобальные
   свойства CMake, пути сделав абсолютными от CMakeLists, где написан
   запрос.
2. **Отложенный вызов.** Тот же файл просит CMake вызвать
   `_dgx_fonts_finish` в самом конце обработки корневого CMakeLists
   (`cmake_language(DEFER CALL ...)`), когда все компоненты и `main` уже
   сделали свои запросы. Поэтому порядок компонентов не важен.
3. **Одно правило.** `_dgx_fonts_finish` пишет `build/dgx_fonts/needs.txt`
   (только если он изменился) и заводит одно правило сборки: команда —
   `python dgx_fonts.py build needs.txt build/dgx_fonts`, входы — тексты
   запросов, файлы шрифтов, правила, сам скрипт и `font2c.c`, выходы —
   `dgx_fonts.c` и `dgx_fonts.h`. Выходы приписываются к библиотеке DGX
   (`target_sources`), каталог — к её публичным путям включения, и
   библиотека зависит от правила.
4. **Постоянные имена выходов.** CMake должен знать список исходников на
   конфигурации, а шрифты становятся известны только на сборке. Раньше
   это и не давало сделать «динамический список шрифтов». Теперь список
   не меняется никогда: это всегда два файла, меняется их содержимое.
5. **Скрипт.** На сборке `dgx_fonts.py` читает запросы, собирает буквы,
   находит начертания (`fc-list`, правила), переводит размеры в пиксели,
   собирает `font2c` из исходника DGX, если его ещё нет, пишет список
   шрифтов по строке на запрос и зовёт `font2c -jo` один раз, вместе со
   списками из `dgx_font_list`; `font2c` сам сливает одинаковые шрифты и
   пишет один `.c`. У шрифтов «как есть» скрипт разбирает `glyph_ranges[]`
   из их `.c` и проверяет буквы. Потом пишет `dgx_fonts.c` и `dgx_fonts.h`,
   только если они изменились.
6. **Что пересобирается.** Изменился текст — правило запускается, и если
   шрифт изменился, перекомпилируется один `dgx_fonts.c`; заголовок при
   тех же запросах тот же, поэтому зависящие от него файлы не трогаются.
   Файл только тронут — правило отработает, ничего не перепишет и не
   перекомпилирует. Новый запрос в CMakeLists — переконфигурация сама, как
   при любой правке CMakeLists, и так же при правке списка из
   `dgx_font_list`. Начертания, которые нашли fontconfig и правила,
   названы в depfile (CMake 3.20 и новее), поэтому изменённое начертание
   тоже пересобирает шрифты. Начертание, установленное заново или
   положенное в каталог, откуда правила берут начертания, не видно, пока
   не изменится один из этих файлов: тронь правила, и шрифты сделаются
   заново.

Проверено на ESP-IDF 5.5 и 6.0 (CMake 3.30 и 4.0): запросы из компонента
и из `main` в одном правиле, перекомпиляция одного файла при смене текста,
ничего при касании файла.
