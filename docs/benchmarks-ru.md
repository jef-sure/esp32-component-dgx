## Тест

В TFT_eSPI тест лежит в `examples/320 x 240/TFT_graphicstest_PDQ`, в
LovyanGFX тот же скетч — `examples/Test/TFT_graphicstest_PDQ`. Его сделал
Xark из `graphicstest` Adafruit для своей библиотеки PDQ_GFX. Каждая строка
его таблицы — время одного вида рисования на чёрном экране:

| Строка | Что рисуется и что измеряется |
| --- | --- |
| HaD pushColor | Логотип Hackaday, 240x320 пикселей отрезками двух цветов, 16 раз, в одно окно; `pushColor()` — вызов TFT_eSPI, который отправляет отрезок пикселей одного цвета |
| Screen fill | Весь экран заливается 5 раз, время делится на 5 |
| Text | Строки текста шрифтом 5x7 в размерах 1, 2, 3, 5 и 6 |
| Pixels | Каждый пиксель экрана ставится отдельно, каждый своим цветом |
| Lines | Линии из каждого угла в каждый шестой пиксель дальних сторон, сумма по четырём углам |
| Horiz/Vert Lines | Горизонтальная линия через каждые 5 строк и вертикальная через каждые 5 столбцов |
| Rectangles (outline) | Квадраты вокруг середины, каждый на 6 пикселей больше |
| Rectangles (filled) | Те же квадраты залитые, с самого большого, каждый замеряется отдельно |
| Circles (filled) | Залитые круги радиуса 10 по всему экрану |
| Circles (outline) | Окружности радиуса 10 по всему экрану и за его краями |
| Triangles (outline) | Треугольники вокруг середины, каждый на 5 пикселей больше |
| Triangles (filled) | Те же треугольники залитые, каждый замеряется отдельно |
| Rounded rects (outline) | Квадраты со скруглением радиусом в 1/8 стороны |
| Rounded rects (filled) | Те же квадраты залитые |

Собственный `graphicstest` Adafruit устроен иначе: заливка в нём — сумма
пяти заливок, у линий остаётся только время четвёртого угла, логотипа и
теста пикселей нет. Его числа — не числа теста PDQ.

Тест PDQ шёл на каждой библиотеке в том виде, в каком он опубликован, с
такими изменениями:

- **Везде:** пины платы и прототипы функций, которые добавляет к скетчу
  Arduino IDE, чтобы он собирался как файл C++.
- **LovyanGFX:** класс панели этой платы вместо того, который угадывает
  `LGFX_TFT_eSPI.hpp`. Его скетч вызывает `startWrite()` один раз и не
  заканчивает его, то есть держит шину SPI весь прогон; скетч TFT_eSPI
  берёт шину на каждый вызов.
- **Adafruit_ILI9341**, в котором теста PDQ нет: скетч TFT_eSPI, где
  отрезки логотипа идут через `writeColor()` (у Adafruit_GFX нет
  `pushColor()` со счётчиком), а пиксели — через `writePixel()` внутри
  `startWrite()`, потому что `drawPixel()` у Adafruit берёт шину сам.

DGX рисует те же фигуры тех же размеров и цветов в том же порядке. Где
у DGX нет одного вызова на фигуру, тест делает то, что сделала бы
программа: горизонтальная или вертикальная линия — это
`dgx_fill_rectangle()` высотой или шириной в пиксель, контур треугольника —
три `dgx_draw_line()`, логотип идёт через `set_area()` и `write_area()`
экрана, текст — шрифтом `GLCD5x7`, тем же, что у других библиотек, в тех
же размерах. Время заканчивается, когда у дисплея есть последний пиксель:
DGX может ещё передавать, когда вызов вернулся, поэтому часы читаются после
`scr->wait_buffer()`. Другие библиотеки возвращаются из этих вызовов, когда
шина уже свободна.

## Нарисовано в памяти и отправлено

Как ни быстра шина, то, что рисуется на панели по частям, видно по частям.
Без мигания выводится только картинка, готовая заранее и отправленная
целиком: виртуальный экран или подготовленное изображение. Поэтому
программа на DGX рисует фигуры в памяти и отправляет результат. Тест
прогоняется второй раз именно так. Каждый тест рисует свою картинку в 8-битный виртуальный экран размером с дисплей, время
берётся как раньше, и к нему прибавляется одна отправка всего экрана на
дисплей через таблицу из 256 цветов, RGB332. 16-битный экран 240x320 — это
150 КБ, у CYD столько одним куском свободно не бывает. TFT_eSPI тоже
хранит 8-битные спрайты как RGB332, и его скетч, прогнанный так же, стоит
рядом с DGX: тесты рисуют в 8-битный спрайт размером с экран, и к времени
каждого прибавляется `pushSprite()`.

## Что делает шина SPI в DGX

До 0.9.3 включительно DGX отправлял каждую передачу через драйвер SPI
master из ESP-IDF, а драйвер начинает передачу гораздо дольше, чем провод
передаёт несколько байт. Окно, у которого меняются только столбцы, и один пиксель на SPI — это четыре
передачи: команда столбцов, её четыре байта, команда записи в память и
пиксель. Замеры на CYD, среднее по 1000:

| Что | мкс |
| --- | ---: |
| Один байт через `spi_device_polling_transmit()`, хост с DMA | 12,3 |
| То же на хосте без DMA | 10,6 |
| То же с заранее захваченной шиной | 8,3 |
| `spi_device_acquire_bus()` и `spi_device_release_bus()` | 6,9 |
| Один байт через регистры хоста | 0,95 |
| Окно и пиксель через регистры хоста | 4,7 |

Теперь дисплей держит шину от окна до конца своего рисования, и пока
держит, короткие передачи идут через регистры хоста: команды, их короткие параметры
и пиксели до 256 байт, передачами по 60 байт — целыми пикселями по 2, 3 и
4 байта. `spi_device_acquire_bus()` настраивает хост на устройство; перед
первой передачей через регистры после передачи драйвера хост
перенастраивается для них. Пиксели длиннее идут через драйвер с DMA, как и
раньше, и процессор заполняет следующий кусок, пока уходит этот.

- **Когда шина отпускается.** Дисплей из `dgx_spi_init()` или
  `dgx_qspi_init()` один на хосте, который поднял DGX, и держит шину
  между рисованиями: захват стоит 6,9 мкс, больше пикселя. Второй дисплей
  DGX на этом хосте заставляет первый отпустить шину, и дальше они берут её
  по очереди на каждое рисование. Дисплей из `dgx_spi_init_on_bus()` или
  `dgx_qspi_init_on_bus()`
  отпускает шину в конце каждого рисования или пачки вокруг него — для
  других устройств на хосте программы.
- **QSPI** посылает перед данными код операции и адрес по одной линии, а
  данные — по одной линии для параметров и по четырём для пикселей, так
  что окно со своими пикселями переключается между одной и четырьмя
  линиями почти на каждой передаче. `spi_ll_master_set_line_mode()` пишет
  дюжину полей регистров, а на ESP32-S3 каждое поле — это ещё и чтение
  регистра: передача команды с четырьмя байтами шла так 5,8 мкс, а с
  записью одного поля, которое различает эти два случая, — 3,0 мкс.
- **Запись регистров целиком**, а не по полям, дала бы на CYD 0,77 мкс на
  байт вместо 0,95 — так делает TFT_eSPI. Но раскладка регистров у чипов
  разная, а DGX держится функций `spi_ll_*` из ESP-IDF, которые есть для
  всех чипов.

Заливка 1,2 МБ занимает 3,5 мс. Каждое рисование вне пачки заканчивается

треугольник записывает сотни килобайт, отдельный пиксель — одну строку

и пиксели. Пачка вокруг многих рисований записывает кэш один раз, а
картинка, нарисованная в памяти, — один раз при отправке.

Логотип стоит другого: пока он рисуется, кэш не записывается. Панель имеет
размер 1024x600, а тест идёт на повёрнутом экране, поэтому соседние пиксели
ряда лежат в кадровом буфере через 2 КБ, каждый в своей строке кэша, и
`write_area()` переносит их по одному: всего 1,4 мкс на пиксель. Картинка,
отправленная из памяти целиком, идёт в порядке панели.

## Где DGX ещё медленнее

Скоростью мелких фигур DGX пожертвовала сознательно: любое рисование идёт
через функции экрана и шины, и один код обслуживает все виды дисплеев. Вот
чего это стоит.

Маленькая фигура — это много окон. Сколько стоит одно, показывает тест
пикселей: отдельный пиксель — это окно и два байта, 8,5 мкс у DGX на CYD,
2,9 мкс у TFT_eSPI и 3,0 мкс у LovyanGFX. Те же четыре передачи через
регистры, без всего остального, шли 4,7 мкс. Остальное:

- **Передачи** стоят по 1,2 мкс против примерно 0,7: функции `spi_ll_*`
  пишут поля регистров, и каждая такая запись — ещё и чтение регистра, а
  TFT_eSPI пишет регистры ESP32 целиком.
- **Функции экрана и шины**, через которые идёт окно: `set_area()`
  экрана, команды шины, запомненное окно, чтобы не слать заново
  неизменившиеся границы. Тот же код рисует на виртуальном экране, на
  дисплее QSPI или DSI; TFT_eSPI написан под одну свою шину.
- **Отдельный пиксель** ждёт, пока уйдёт предыдущий, чтобы записать свои
  два байта поверх.
